# 技术备忘录：登录态持久化改造

> 状态：已调研、已定位，暂未实施。当前方案够用，日后如果掉线频率明显上升再照此改造。
> 记录时间：2026-11-11

## 一、要解决的问题

华为云开发者账号的登录态会失效，必须人工重新扫码。以下是一段实测数据（主号日志）：

| 指标 | 数量 |
|---|---|
| 登录成功 | 8 次 |
| 保活时发现失效（logged-out） | 7 次 |
| 保活因网络抖动未完成 | 11 次 |

掉线时间点分散在全天（00:02 / 06:49 / 12:00 / 03:49 / 02:55 / 17:38 / 01:16），
没有固定周期，说明不是简单的定时过期。

## 二、当前实现（需要被替换的部分）

**载体是 `storageState` cookie 快照**

| 文件 | 说明 |
|---|---|
| `runner/storage/huaweicloud-auth.json` | 主号登录态（Playwright storageState 格式） |
| `runner2/storage/huaweicloud-auth.json` | 账号2 登录态 |
| `runner/storage/auth-snapshots/*.json` | 保活成功后的自动快照 |

**流程**：扫码登录 → 存成 JSON → 每次任务 `browser.newContext({ storageState })` 导入 → 用完即弃。

**已实现的保护**（2026-11-11 新增）：
- `scripts/browser-lock.sh` / `browser-lock.mjs` —— 同账号浏览器互斥锁（flock），
  已接入：登录守护、积分采集、鸿蒙预热
- `grow-api.mjs` / `auth-utils.mjs` —— 导航遇 `ERR_NETWORK_CHANGED` 自动重试

## 三、根因分析（调研结论）

### 3.1 为什么快照方式先天不足

华为云的登录 cookie 分两类：

| 类型 | 例子 | storageState 能否保住 |
|---|---|---|
| 持久 cookie（有 expires） | `_frid`、`cbc-sid`、`vk` | ✅ 能 |
| **会话 cookie（expires=-1）** | **`SessionID`、`SSOTGC`** | ❌ **不能** |

而 **SSO 换票依赖的恰是会话 cookie**。每次开新浏览器 = 拿半套凭证访问。

### 3.2 `SSOTGC` 会被"消费"

华为云社区博客（https://bbs.huaweicloud.com/blogs/dae2cdfb159a493cb273ee99a6559bf1）实测：

> `SSOTGC` 每次走 SSO 换 ticket 都会消费一次；多个浏览器上下文共享同一份
> `storage_state` 时，先换到 ticket 的上下文会把 TGC 用掉，其他上下文再访问
> 就会突然回落到"登录/注册"。

**这解释了"莫名其妙被踢"**：本机有 4 个组件各自开浏览器（登录守护 30 分钟 /
积分采集 30 分钟 / 鸿蒙预热 5 分钟 / 面板按需），互不协调 → 互相把票用掉。

**已用互斥锁缓解**（见二），但这是"止血"，不是根治。

### 3.3 哪些 cookie **不是**登录凭据（重要）

开源项目 `dddmiku/hwcloud-console` 把以下 cookie 列入"可安全丢弃、不用于判断登录态"白名单：

```
SessionID / _frid / cbc-sid / vk / _fr_ssid / HWWAFSESID / HWWAFSESTIME / cf / csrf-eco / ua
```

另一个来源（https://bbs.huaweicloud.com/blogs/520910）实测：
`cbc-sid` 的 expires 写到 **2027 年**，接口照样 `403 not login`。

**结论：不要拿 `_frid/cbc-sid/vk` 的过期时间判断登录态**（我们之前可能一直在误判）。
真正的判据应是：业务接口是否返回 `403 not login` / 是否拿到 `csrf` 响应头。

### 3.4 客户端**无法**阻止服务端主动作废

OWASP Session Management Cheat Sheet：

- 会话过期**必须服务端强制**，客户端改 cookie / 延长 expires 无效
- 除了 **Idle Timeout**（可用心跳延长），标准做法还有 **Absolute Timeout**
  （无论是否活动，到点就失效 —— 心跳无效）
- 服务端可**绑定 IP / UA 到会话**，检测到变化即终止

华为云官方文档也**从未承诺**长期登录态，反而写明「"信任"环境会根据您的实际
使用情况及使用时间发生变化」（https://support.huaweicloud.com/account_faq/faq_id_0048.html）。

### 3.5 已排除的怀疑

- ❌ **无头 UA**：调研提到"无头 UA 带 HeadlessChrome 会被 WAF 拦"。
  实测本机 Playwright 默认 UA **不含** HeadlessChrome，正常 UA 与自定义真实 UA
  都能登录成功 → **不是本机的原因**
- ❌ **延长 cookie expires**：确定无效（见 3.3 实证）
- ❌ **提高保活频率**：有害。`hwcloud-console` 作者实测高频保活 + 自动登录
  → 出口 IP 被限流 **429「登录尝试过于频繁」**，最终**主动停用了 20 分钟定时保活**
- ❌ **「信任浏览器」免验证码**：官方确有该功能，但出现在**「验证码登录」**流程；
  我们用的是**扫码登录**，实测登录页上**没有「信任」按钮** → 不适用

## 四、改造方案（日后实施时照此执行）

### 方案：`launchPersistentContext` 持久化 profile + 单进程

**核心思路**：不再"每次新开浏览器 + 导 cookie 快照"，而是给每个账号一个
**专属浏览器数据目录**，所有任务共用它。

**收益**：
1. 会话 cookie 天然留在 profile 里，不会丢
2. 浏览器指纹（UA / 时区 / 各类标识）保持一致 → 服务端看到"同一个人"
3. 省掉每次导入 cookie 的环节，也就没有导入丢失

**代价**：
- 需**重新扫码一次**（建立新 profile）
- 改动面较大（见下方"要改的位置"）

### 要改的位置清单（按依赖顺序）

| # | 文件 | 改什么 |
|---|---|---|
| 1 | `scripts/browser-utils.mjs` | 新增 `launchPersistent(accountId)`：用 `chromium.launchPersistentContext(userDataDir, ...)`，profile 目录建议 `storage/profiles/<acc>` |
| 2 | `scripts/auth-utils.mjs` | `openGrowAndCheckLogin` 等改为接收 persistent context；去掉 `storageState` 导入 |
| 3 | `scripts/login-daemon.mjs` | 扫码流程写入 persistent profile；保活复用它 |
| 4 | `scripts/points-snapshot.mjs` | 同上（`GrowApi` 的 `#page()` 拿 context 的方式要改） |
| 5 | `scripts/grow-api.mjs` | `#page()` 支持传入已有 context，不再自己 `newContext` |
| 6 | `scripts/devspace-py-style.mjs`<br>`harmony-daily.mjs`<br>`scripts/tasks/bbs-article.mjs` | 各任务的浏览器创建点（**共 217 处 `newContext`**，建议先只改高频路径） |
| 7 | `scripts/browser-lock.sh/.mjs` | **保留**！持久化之后仍需串行（profile 不能并发打开） |
| 8 | `scripts/auth-doctor.mjs` | 「会话 cookie 续期」那段可废弃（持久化后不需要手工续期） |
| 9 | `control/harmony-oauth.mjs` | 预热也用 persistent profile |

### 实施注意事项

- **profile 目录不能用日常 Chrome 的 User Data**（Playwright 官方警告：
  可能导致页面不加载或浏览器直接退出），必须独立目录
- 同一 profile **不能并发打开** → 必须配合已有的互斥锁
- 建议**先在登录守护 + 采集这两条链上试点**，跑一两天验证，再推广到任务脚本
- 持久化后**仍需预期偶尔掉线**：服务端 absolute timeout 客户端无法对抗，
  现实目标是「把人工扫码从每天降到尽量少」

## 五、当前决定

**暂不实施。** 理由：
1. 互斥锁刚上线几小时，效果未观察（这是唯一有明确机制依据的修复）
2. 持久化改动大（217 处 `newContext`），且需重新扫码
3. 如果互斥锁已解决主因，持久化的增量收益有限

**观察指标**：`login-daemon-*.log` 里「保活时发现失效」的出现频率。
若明显下降 → 就维持现状；若仍频繁 → 按本备忘录第四节实施。
